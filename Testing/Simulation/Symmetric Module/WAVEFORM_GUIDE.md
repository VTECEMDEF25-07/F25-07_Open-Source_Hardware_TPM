# Testing the symmetric modules

Author: Generated by Codex  
Date: October 13, 2026

Each script compiles the required files, checks the results automatically,
records a waveform file, and leaves the Wave window open when run in Questa's
GUI. Run the commands below in the **Questa Transcript window**, one at a time.
If a simulation is already loaded, enter `quit -sim` first. Then run the next
script. These commands use absolute paths, so your current directory does not
matter.

## 1. Start with the CFB block

```tcl
do {<repository>/Testing/Simulation/Symmetric Module/run_cfb_block.do}
```

This uses real AES and checks a NIST AES-256/CFB128 example.

| `test_case` | What happens |
|---|---|
| 1 | Encrypt known plaintext; change inputs after acceptance to test capture |
| 2 | Decrypt known ciphertext; hold start high to check no replay |
| 3 | Encrypt five bytes; unused output bytes become zero |
| 4 | Decrypt five bytes; feedback uses incoming ciphertext |
| 5 | Empty input returns the IV without starting AES |
| 6 | Reject 17 bytes without starting AES |
| 7 | Reset during AES, then run a fresh successful operation |

Follow the waveform in this order:

1. `start_i` is accepted and `wait_o` rises.
2. `aes_init_r` launches key expansion; `aes_ready_w` falls then rises.
3. `aes_next_r` launches encryption of the feedback/IV.
4. `cipher_stream_block_w` is the AES-produced mask.
5. `cfb_result_w` is input XOR mask, with unused bytes cleared.
6. `done_o` pulses with the final data and feedback.

Case 1 expects ciphertext `dc7e84bfda79164b7ecd8486985d3860`.
Case 2 expects plaintext `6bc1bee22e409f96e93d7e117393172a`.

## 3. Test the session parameter controller

```tcl
do {<repository>/Testing/Simulation/Symmetric Module/run_session_parameter_controller.do}
```

This uses the existing **fake HMAC** and a **mock CFB worker**. It verifies
the prepared messages and controller behavior, not real HMAC/KDFa cryptography.

| `test_case` | What happens |
|---|---|
| 1 | Capture CFB session inputs despite later caller changes |
| 2 | CFB decryption request and held start |
| 3 | Derive XOR mask and apply it |
| 4 | Reverse XOR using the same mask |
| 5 | Five-byte XOR requests 40 output bits |
| 6 | Empty XOR skips HMAC and CFB |
| 7 | Reject invalid session |
| 8 | Reject both job direction flags set |
| 9 | Reject non-CFB mode on the CFB path |
| 10 | Reject more than 16 bytes |
| 11 | Inject HMAC error on the second digest; no CFB launch |
| 12 | Reset during derivation and recover |

For CFB, expect HMAC counters 1 and 2, label `43464200` (`CFB` plus zero),
and requested length 384 bits. Then `cfb_start_o` sends the derived key and IV.

For XOR, expect one HMAC request, label `584f5200` (`XOR` plus zero), and
requested length `data_bytes*8`. `cfb_start_o` stays low. The controller
applies the derived mask directly.

States: 0=IDLE, 1=DERIVE, 2=WAIT_KDF, 3=ISSUE, 4=WAIT_CFB,
5=DONE, 6=RELEASE.

## Reading and saving the waves

- Look at `test_case` to identify the scenario.
- Clocked transfers happen at rising edges. Zoom into the selected case.
- `done_o` is a one-cycle pulse; inspect the result at that pulse.
- A `PASS` message means assertions checked the expected behavior. A picture
  alone cannot establish correctness.
- Each run creates its own directory and prints its `vsim.wlf` and transcript
  locations. The three new module tests save under
  `<repository>/build/symmetric-module/`.
- To reopen a recording, use Questa **File > Open** and select its `.wlf` file.
  The signal values are preserved; you may need to add the desired signals
  from the recorded hierarchy to the Wave window again.

These tests exercise the symmetric RTL with test inputs. Host TPM command
handling and authorization require separate integration tests.
